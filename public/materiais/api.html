Pedir e Esperar

Na aula passada o app perguntou um CEP para a internet. Hoje ele também manda dados para lá. Nos dois casos a resposta demora, e o código precisa esperar por ela. Para isso servem o async e o await.

Parte 1 · Entender
1

Toda conversa com uma API tem duas metades

O app manda uma requisição e o servidor devolve uma resposta. A requisição diz o que você quer fazer (o método) e com quem (a URL). Às vezes ela leva junto um dado, chamado corpo. A resposta sempre volta com um status, um número que diz se deu certo, e quase sempre com um corpo em JSON.

O método é um verbo. Cada um corresponde a um comando SQL que vocês já usaram no app dos bordeis. Muda o lugar onde o dado mora, do celular para um servidor, mas as quatro operações são as mesmas.

E os status que vão aparecer hoje: 200 e 201 deram certo; 404 é URL errada (o recurso não existe); 500 é problema do lado do servidor. Sem internet não tem status nenhum, porque a resposta nem chega.

2

A internet demora, e o código não espera sozinho

O JavaScript executa uma linha atrás da outra, muito rápido. Uma linha que vai à internet leva centenas de milissegundos, às vezes segundos no 4G. Se ninguém mandar esperar, a próxima linha roda antes da resposta chegar e tenta usar uma coisa que ainda não existe.

Rode as duas versões abaixo. A barra azul é a internet trabalhando.

Sem await, a variável resposta guarda uma Promise, que ainda não é a resposta. A linha seguinte procura .json() nela, não encontra, e o app mostra a tela vermelha. A internet continua trabalhando depois do erro, e a resposta chega 1600 ms depois, quando a função já parou.

3

Promise é a senha da lanchonete

Você pede um lanche e o caixa te entrega uma senha. A senha é a promessa de que o lanche vai chegar. Com ela na mão você tem duas opções: ficar parado olhando o painel até chamarem o número, ou sair e esquecer, e aí o lanche fica no balcão.

fetch(API)
Faz o pedido e devolve na hora a senha, a Promise. A resposta ainda não está ali.
await
Fica olhando o painel. A função pausa nesta linha até a promessa se cumprir, e só então segue com o valor de verdade.
resposta
O lanche chegou. É um objeto com status, ok e o corpo, que ainda precisa virar objeto com resposta.json().

await só funciona dentro de função async

A palavra async antes de function avisa que esta função pode parar no meio para esperar. Sem o async, o Expo nem compila e aponta a linha do await.

São dois await, e os dois são necessários

O primeiro espera os cabeçalhos da resposta, onde está o status. O corpo ainda pode estar chegando aos pedaços, por isso resposta.json() também devolve uma Promise e também leva await.

Enquanto uma função espera, o app não trava

Só carregar() fica parada. A tela continua respondendo ao toque, e é por isso que dá para mostrar um girador de carregando durante a espera.

// a forma que vamos usar sempre:
async function carregar() {
  const resposta = await fetch(API);      // espera o status
  const dados = await resposta.json();  // espera o corpo virar objeto
  setLista(dados);                       // a tela redesenha
}
4

Por que o JavaScript espera diferente

No jeito mais comum de buscar uma URL em PHP ou Java não tem await. A linha que vai à internet para o programa até a resposta chegar, e a próxima linha já recebe o dado pronto: 

// PHP: o programa para nesta linha até a resposta chegar
$dados = json_decode(file_get_contents($api));

// Java: a thread para nesta linha
HttpResponse<String> resposta = client.send(req, BodyHandlers.ofString());

Isso se chama bloquear. Funciona bem num servidor porque, na configuração mais comum, cada requisição ganha a sua própria thread (no Java) ou o seu próprio processo (no PHP). Enquanto uma fica parada esperando, as outras seguem trabalhando. Java também tem jeitos de não bloquear, mas a primeira forma que se aprende é essa.

O JavaScript nasceu em 1995 dentro do navegador, e o código de uma página roda em uma thread só. Essa mesma thread desenha a página, responde aos cliques e roda o seu código. Se uma requisição bloqueasse essa thread, a página inteira congelaria até a resposta chegar, sem rolar, clicar ou digitar. Por isso o fetch não bloqueia. O código entrega a requisição para o navegador, segue rodando, e o navegador avisa quando a resposta chega.

No celular a regra é a mesma, e vale até no Android nativo. Desde o Android 3.0, um app em Java ou Kotlin que faz rede na thread principal (a que desenha a tela) é derrubado com NetworkOnMainThreadException. Lá o programador precisa abrir outra thread, ou usar as coroutines do Kotlin. No React Native o seu JavaScript roda numa thread só, e quem faz a requisição de verdade é o código nativo do aparelho (no Android, a biblioteca OkHttp).

Três jeitos de escrever "me avisa quando chegar"

Como o JavaScript não pode parar, por muitos anos o jeito era passar uma função para ser chamada depois, o callback. Com várias requisições em sequência, os callbacks ficavam um dentro do outro. Em 2015 a linguagem ganhou a Promise, e em 2017 o async/await, ideia copiada do C#, que já tinha essas duas palavras desde 2012. As três versões abaixo fazem a mesma coisa: 

// até ~2015: callback (XMLHttpRequest)
const xhr = new XMLHttpRequest();
xhr.open("GET", API);
xhr.onload = function () {
  setLista(JSON.parse(xhr.responseText));   // chamada quando a resposta chega
};
xhr.send();

// 2015: Promise com .then
fetch(API)
  .then((resposta) => resposta.json())
  .then((dados) => setLista(dados));

// 2017: async/await, o que usamos
async function carregar() {
  const resposta = await fetch(API);
  const dados = await resposta.json();
  setLista(dados);
}

O await deixa o código com cara de Java ou PHP, uma linha depois da outra, sem bloquear nada. Quando a função chega num await, a função fica suspensa e a thread fica livre para a tela trabalhar. Quando a resposta chega, a função continua daquela linha. Por baixo, cada await ainda é um .then.

A tela, inteira

    

    

      

        Arquivo novo src/app/bordeis-api.js, mais um link na tela inicial. Compare com o
        bordel.js da aula 10: o listar() virou carregar() com
        GET, e o salvar() virou um POST.
      


const API = "https://SEU-ID.mockapi.io/api/v1/bordeis";

// GET: pede a lista inteira para a API.
async function carregar() {
  setCarregando(true);
  try {
    const resposta = await fetch(API);
    if (!resposta.ok) {
      setErro(`A API respondeu ${resposta.status}.`);
    } else {
      const dados = await resposta.json();
      setLista(dados);
      setErro("");
    }
  } catch {
    setErro("Sem conexão com a API.");   // sem internet: nem chega resposta
  }
  setCarregando(false);
}

// POST: manda um bordel novo. O corpo vai como TEXTO em JSON.
async function salvar() {
  if (!nome.trim() || !cor.trim()) {
    setErro("Preencha nome e cor.");
    return;
  }
  try {
    const resposta = await fetch(API, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ nome: nome, cor: cor }),
    });
    if (!resposta.ok) {
      setErro(`Não salvou: a API respondeu ${resposta.status}.`);
    } else {
      setNome("");
      setCor("");
      carregar();                         // a lista não sabe do novo: pergunta de novo
    }
  } catch {
    setErro("Sem conexão com a API.");
  }
}

useEffect(() => { carregar(); }, []);   // GET ao abrir a tela

// na FlatList: puxar para baixo chama carregar(), e o girador usa o estado
<FlatList data={lista} refreshing={carregando} onRefresh={carregar} … />


      

        
Onde cada erro é tratado

        
Demora: o estado carregando liga o girador da lista.
        Servidor respondeu, mas mal (URL errada, 404): resposta.ok é
        false. Nem chegou resposta (Wi-Fi desligado): o
        fetch lança um erro e o catch pega. Testem os três em aula: errem
        uma letra da URL e desliguem o Wi-Fi.

Erros comuns

    

    

      

        

          
resposta.json is not a function

          
Faltou o await antes do fetch. A variável guarda a senha (a Promise), e a senha não tem .json().

        

        

          
Unexpected reserved word 'await' ao compilar

          
A função não tem async. Coloque antes de function.

        

        

          
O POST deu certo, mas o bordel aparece vazio, sem nome e sem cor

          
Faltou o JSON.stringify no body ou o header Content-Type. O servidor não entende o corpo, e o bordel fica só com id e createdAt, ou a API responde com erro.

        

        

          
Salvou, mas a lista na tela não mudou

          
Faltou chamar carregar() depois do POST. O item novo está no servidor, e o estado do app ainda guarda a lista antiga.

        

        

          
A tela mostra A API respondeu 404.

          
A URL está errada: confira o id do projeto, o prefixo e o nome do recurso (bordeis, minúsculo e no plural, igual ao MockAPI).

        

        

          
Os campos aparecem com outro nome, ou undefined

          
O nome do campo no MockAPI tem que ser igual ao do código. Nome e nome são campos diferentes.
