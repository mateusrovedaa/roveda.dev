Banco no Aparelho

Por que a lista de tarefas some quando o app fecha, e como o SQLite guarda os dados num arquivo dentro do próprio celular para que eles continuem lá na próxima vez.

projeto da aula: 9-aula2509 · npx expo install expo-sqlite && npm start
Parte 1 · O problema
1

O estado vive na memória

A tela /lista guarda as tarefas em estado:

const [lista, setLista] = useState([]);

function adicionar() {
  setLista([...lista, texto]);
  setTexto("");
}

Funciona enquanto o app está aberto. O estado fica na memória RAM, a memória de trabalho do celular. Quando o app fecha, o sistema libera essa memória e tudo que estava nela vai junto.

Para os dados sobreviverem ao fechamento, eles precisam ser gravados no armazenamento do aparelho, num arquivo. É o mesmo motivo pelo qual um documento não salvo se perde quando o computador desliga.

2

Por que SQLite

Um banco de dados é um programa que guarda dados organizados e responde perguntas sobre eles: "me dê todas as tarefas, das mais novas para as mais antigas". Bancos como MySQL e PostgreSQL rodam num servidor e o app conversa com eles pela internet.

O SQLite é um banco que roda dentro do próprio app e guarda tudo num único arquivo. Não tem servidor, não precisa de internet, não precisa de senha. Ele já vem instalado em todo Android e iPhone. É o banco mais usado do mundo: o WhatsApp, o navegador e boa parte dos apps do seu celular guardam dados assim.

Onde guardar Serve para
Estado (useState) o que só importa enquanto a tela está aberta: o texto sendo digitado, um botão ligado
SQLite listas de registros que precisam continuar no aparelho: tarefas, notas, contatos
Servidor dados que outras pessoas ou outros aparelhos precisam ver

Os dados do SQLite ficam só naquele celular. Outro aparelho, mesmo com o mesmo app, tem o próprio arquivo e as próprias tarefas.

Parte 2 · Como o banco pensa
3

Tabela, linha e coluna

O SQLite organiza os dados em tabelas, como uma planilha. Cada coluna é um dado com nome e tipo. Cada linha é um registro.

idtexto
1Estudar para a prova
2Entregar o exercício
3Comprar pão

Esta é a tabela tarefas, dentro do arquivo tarefas.db. Um arquivo pode ter várias tabelas.

O id é um número que identifica cada linha, e o próprio banco escolhe. Duas tarefas podem ter o mesmo texto, mas nunca o mesmo id. É por ele que o app aponta uma tarefa específica.

4

SQL, a língua do banco

O app não mexe no arquivo diretamente. Ele manda comandos em SQL e o SQLite executa. Nesta aula são três comandos.

Criar a tabela

CREATE TABLE IF NOT EXISTS tarefas (
  id    INTEGER PRIMARY KEY AUTOINCREMENT,
  texto TEXT NOT NULL
);
IF NOT EXISTS só cria se a tabela ainda não existir. Sem isso, a segunda abertura do app daria erro
INTEGER, TEXT o tipo da coluna: número inteiro, texto
PRIMARY KEY esta coluna identifica a linha: não se repete
AUTOINCREMENT o banco preenche sozinho: 1, 2, 3...
NOT NULL a coluna não pode ficar sem valor

Inserir uma linha

INSERT INTO tarefas (texto) VALUES ('Comprar pão');

Só o texto é informado. O id o banco gera.

Consultar

SELECT * FROM tarefas ORDER BY id DESC;

* quer dizer "todas as colunas". ORDER BY id DESC ordena pelo id do maior para o menor: a tarefa mais nova aparece primeiro.

Parte 3 · No código
5

Abrir o banco

npx expo install expo-sqlite

expo install em vez de npm install: ele escolhe a versão que combina com o Expo do projeto. 

import * as SQLite from "expo-sqlite";

// fora do componente
const db = SQLite.openDatabaseSync("tarefas.db");

db.execSync(`
  CREATE TABLE IF NOT EXISTS tarefas (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    texto TEXT NOT NULL
  );
`);

openDatabaseSync abre o arquivo. Se ele não existe, cria vazio. execSync executa SQL que não devolve nada, como o CREATE TABLE.

As duas linhas ficam fora da função do componente. A função do componente executa a cada render (material Tela Viva). Dentro dela, o banco seria aberto de novo a cada tecla digitada. Fora, o código executa uma vez, quando o arquivo lista-db.js é carregado.

O final Sync quer dizer que a função espera o banco terminar antes de seguir para a próxima linha. Para poucas tarefas é instantâneo. Existem versões Async para quando o volume de dados é grande.

6

Inserir sem colar texto no SQL

function adicionar(texto) {
  db.runSync("INSERT INTO tarefas (texto) VALUES (?)", [texto]);
}

runSync executa um comando que altera o banco. O ? marca um lugar vazio. A lista do segundo argumento preenche os lugares, na ordem.

Parece mais simples juntar o texto direto no comando:

// NÃO faça assim
db.runSync("INSERT INTO tarefas (texto) VALUES ('" + texto + "')");

Se o usuário digitar Ler 'Dom Casmurro', o comando vira VALUES ('Ler 'Dom Casmurro''). O apóstrofo do texto fecha as aspas do SQL antes da hora e o banco dá erro. Pior: alguém pode digitar um pedaço de SQL de propósito e o banco executa. Esse ataque se chama SQL injection.

Com ?, o texto vai separado do comando. O banco sabe que aquilo é só um valor, qualquer que seja o conteúdo. Todo valor que vem do usuário entra por ?.

7

Consultar

function listar() {
  return db.getAllSync("SELECT * FROM tarefas ORDER BY id DESC");
}

getAllSync executa um SELECT e devolve uma lista. Cada linha da tabela vira um objeto, com uma propriedade por coluna: 

[
  { id: 3, texto: "Comprar pão" },
  { id: 2, texto: "Entregar o exercício" },
  { id: 1, texto: "Estudar para a prova" },
]

É uma lista comum de JavaScript. Dá para entregar direto para a FlatList.

8

Banco e estado juntos

A tela continua sendo desenhada a partir do estado. O banco não avisa o React quando muda. Quem avisa é o setLista. Por isso, depois de mexer no banco, a tela lê tudo de novo e guarda no estado. 

const [texto, setTexto] = useState("");
const [lista, setLista] = useState([]);

function carregar() {
  setLista(listar());
}

// uma vez, quando a tela abre
useEffect(() => {
  carregar();
}, []);

function salvar() {
  adicionar(texto);
  setTexto("");
  carregar();
}
toque→ INSERT→ SELECT→ setLista→ render

O banco é onde os dados ficam. O estado é o que a tela mostra agora. O useEffect com [] faz a ponte na abertura. carregar() faz a ponte depois de cada alteração. 

<FlatList
  data={lista}
  keyExtractor={(item) => String(item.id)}
  renderItem={({ item }) => <Text>{item.texto}</Text>}
/>

Agora cada item é um objeto, então o texto está em item.texto. keyExtractor diz à FlatList como identificar cada item: o id do banco, que nunca se repete. Ele vira String porque a chave precisa ser texto.

Parte 4 · Consulta
9

Erros comuns

Erro: no such table: tarefas.
O CREATE TABLE não executou, ou o nome da tabela está escrito diferente no CREATE e no INSERT/SELECT.
A tela abre vazia, mas as tarefas estavam lá.
Falta o useEffect que chama carregar() na abertura. Os dados estão no arquivo, só não foram lidos.
Toquei em Adicionar e a tarefa só aparece quando reabro a tela.
Falta carregar() depois de adicionar(). A tarefa foi gravada, mas o estado não foi atualizado.
Mudei o CREATE TABLE (nova coluna) e nada mudou.
IF NOT EXISTS: a tabela já existe no aparelho, então o comando não faz nada. Desinstale o app (ou apague os dados dele) para começar com um arquivo novo.
Tarefas em branco aparecem na lista.
NOT NULL impede valor ausente, não texto vazio. "" é um texto, então o banco aceita. Quem deve barrar é o app, antes de chamar adicionar.
Erro ao abrir /lista-db no navegador.
O expo-sqlite na web precisa de configuração extra. Teste no celular com o Expo Go ou no emulador.
